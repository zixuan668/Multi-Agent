## 2. 数据如何流通

**A 创建任务并生成策略 → 用户确认交付 → B 锁定策略并提炼简报 → 用户补充创意要求 → B 调用模型生成 → 用户编辑并保存 → B 准备结构化输入包并记录交付 → 等待 C 真实评估。**

全程沿用原 `task_id`。B 输出保留 `result_id`、`version`、`strategy_result_id`、`strategy_version`、`round_no`、`created_at` 等信息，可追溯创意所依据的策略。补充要求只影响创意表达，不能覆盖 A 的策略。

后端保存不可覆盖的创意版本、人工修改轨迹、反馈和交付快照；当前界面已按最终要求移除历史入口。所有任务接口按 session / `owner_scope` 隔离。

**当前存储仍为进程内存，重启后不保证保留任务和版本，尚未实现数据库持久化。** 停止服务前应导出所需结果。

## 3. 必须明确：哪些仍是模拟或尚未完成

**真实 C 效果评估尚未实现。** 当前“交付检查智能体”已能真实准备输入包、锁定交付版本并记录待评估状态，但不会自动调用真实 C，也不会产生真实评分或评估结论。

开发模式中的“模拟通过／模拟打回”仅验证界面及多轮流程，不代表完成评估。真实反馈入口当前返回 `C_NOT_CONNECTED`；C 的评估服务、调用调度、回调认证和真实反馈接入均需后续完成。

B 目前只做输出格式、字段长度、结构与引用检查，**不调用复核模型，也不执行营销事实与效果内容审查**。`checks.structure=true` 仅代表结构合格；新结果的 `facts`、`constraints`、`semantic_review` 为 `false`，不能解释为内容审查通过。事实、价格、功效、资源、预算等风险评估需要由 C 实现。

## 4. C 开发人员需要完成与对接的内容

1. **实现真实评估智能体**：接收 B 输入包，结合原始需求、策略和创意，输出评分、风险、修改建议及通过／退回结论。
2. **接通真实交付与反馈**：实现评估调用、身份认证及结果回传；用真实结果替代开发模拟，不能直接将模拟接口当正式接口开放。
3. **提供可定位反馈**：至少包含 `target_agent`、`target_path`、`issue`、`suggestion`、`priority`，并关联任务、策略、创意和评估轮次。创意问题交给 B；受众、定位、渠道、预算等策略问题返回 A。
4. **与 B 联调闭环**：真实退回后，由 B 按反馈调用生成模型修订指定内容，保存新版本，再交 C 评估；旧版本保留。最多三轮业务评估，第 3 轮仍退回则终止为 `not_passed`；技术重试不增加业务轮次。

### 对接入口与候选数据

以下路径前缀均为 `/api/tasks/{task_id}/creative/`：

| 入口 | 当前用途 |
| --- | --- |
| `GET package?result_id=...` | 获取待评估输入包。 |
| `POST delivery` | 记录当前版本交付，提交 `base_result_id`。 |
| `POST feedback` | 正式 C 反馈预留入口，尚未接通。 |
| `POST demo-feedback` | 仅显式启用开发模式后可用的模拟反馈入口。 |

输入包包括 `requirements`、完整 `strategy`、完整 `creative`、`task_id`、`round_no`、`evaluation_status` 与 `feedback_trace`。定义见 `src/agents/creative/schemas/evaluation-request.internal.schema.json`。

**该定义是内部候选协议，尚非团队正式公共契约。** C 负责人需与 B 确认评分及反馈结构、认证方式、通过条件和终止规则，再完成真实接入。
