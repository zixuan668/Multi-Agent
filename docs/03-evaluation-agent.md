# 03 · 效果评估智能体

[返回项目总览](../README.md) · [上一模块：创意智能体](02-creative-agent.md) · [团队协作规范](team-collaboration.md)

> 状态：待开发。评估输入 / 输出契约、评分规则及反馈路由尚需团队确认；当前没有完整评估实现或系统评估通过结论。

## 职责与代码归属

- 负责人：成员 C，实际姓名待团队填写。
- 业务代码：[`src/agents/evaluation/`](../src/agents/evaluation/)。
- 提示词：[`prompts/evaluation/`](../prompts/evaluation/)。
- 职责：按已确认的指标、约束与证据复核策略和创意，生成可定位问题的评估意见。
- 边界：不替策略或创意模块生成业务内容，不虚构真实投放效果，不将自身意见冒充人工验收。

## 与现有策略模块的区别

策略模块已有结构校验、业务约束检查及模型辅助复核。这些机制服务于策略交付，**不等于完整评估智能体**。

当前策略任务完成时仍标记 `assessment_status=not_evaluated`，且 `iteration_count=0`。不得将 `status=completed` 或 `termination_reason=strategy_completed` 改写为“三智能体评估通过”。

现有服务配置中出现的轮次上限、阈值等字段也不代表评估规则或调度闭环已经接通。

## 开发前需要团队确认

1. 输入范围：是否同时包含原始需求、完整策略与创意结果，以及如何校验它们属于同一任务和有效版本。
2. 评估规则：指标定义、依据、评分或判定方法、阈值与规则版本；不能仅从已有配置数字推断完整规则。
3. 输出契约：意见、证据、问题位置、反馈目标及失败状态分别如何表达。
4. 反馈路由：哪些问题交回策略、哪些交回创意，由哪一层调度；评估模块不自行修改其他模块结果。
5. 终止机制：轮次、技术重试、版本与退出条件如何区分，如何保留既有结果并防止无限循环。

确认后将输入 / 输出 Schema 放在公共 `packages/contracts/`。目前不创建猜测字段的占位 Schema，不伪造评估分数、投放效果或验收报告。

## 交付检查

- 新单元测试放在 `tests/unit/evaluation/`；创建测试包时包含 `__init__.py`，确保现有 unittest 命令可发现测试。
- 跨模块测试放在 `tests/integration/`，文件名包含 `evaluation` 或明确的反馈链路名称。
- 公开样例放在 `tests/fixtures/evaluation/` 并脱敏；真实评估日志、人工复核记录留在本地 `artifacts/`，按团队要求另行交付。
- 测试覆盖团队确认的规则、事实边界、约束冲突、异常结果和反馈目标，不只验证字段完整。
- 更新本文状态时注明实际测试与人工复核依据；其他模块不得代替负责人填写通过结论。
